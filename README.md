# CRECS property template skill

An AI skill that edits the shared Elementor property-page template of a
[CRE Cloud Solutions](https://crecloudsolutions.com) WordPress site and exports importable
Elementor JSON.

One template serves **every** property on a CRECS site. Property data is never written
into it: the CRECS widgets and the `crecs-property` dynamic tag fetch it from the CRE
Cloud API at render time, keyed by slug. The skill's job is the design; the data layer is
untouched.

It runs on Python 3.9+ and the standard library. No network, no WordPress, no PHP, no CRE
Cloud credentials.

## Install

Copy `crecs-property-template/` into one of:

| scope | path |
| --- | --- |
| one repository | `.claude/skills/crecs-property-template/` |
| every project | `~/.claude/skills/crecs-property-template/` |

```bash
cp -r crecs-property-template ~/.claude/skills/
python3 ~/.claude/skills/crecs-property-template/scripts/crecs_template.py selftest
```

`8/8` means the install is intact. `dist/` holds the same skill packaged for six
assistant surfaces — Claude Code as a skill or a plugin, Claude in the browser, Codex,
ChatGPT, and a loose file kit for ChatGPT without an install. Each carries its own
`INSTALL.md` and a `MANIFEST.sha256`.

## Layout

```
crecs-property-template/   the skill: SKILL.md, references/, assets/, scripts/
dist/                      the six packaged surfaces, generated
tools/                     the three build utilities that need only this repository
docs/                      scope, compatibility sources, the acceptance script
```

`tools/` sits beside the skill rather than inside it on purpose: the packager copies
everything under the skill folder, so anything placed there would ship inside every
package.

## Regenerating

```bash
node tools/build-negative-fixtures.js crecs-property-template
node tools/build-skill-packages.js   crecs-property-template dist
node tools/verify-package.js         dist/claude-code-skill
python3 crecs-property-template/scripts/tests/run_tests.py
```

## Two things this repository cannot do alone

Both are agreements with the plugin repository, not oversights. Read them before
assuming a regeneration is possible here.

### The catalog comes from the plugin

`references/catalog/` is a projection of 1,586 catalogued Elementor controls, and it is
generated by `build-references.js` from a 20 MB catalog that lives in the plugin
repository. That catalog is produced by four PHP extractors needing the plugin source, a
running WordPress and Elementor — the runtime controls cannot be read any other way,
because Elementor's control stacks do not resolve outside a web request.

**When the plugin's controls change**, someone regenerates the catalog there and delivers
the refreshed `references/` here. The skill's `selftest` prints the CRECS version, the
Elementor version and the plugin revision it was built against; if a client site runs
something else, control names, options and responsive flags may differ.

### The plugin depends on this repository, not only the reverse

The plugin's preview module validates documents against
`includes/preview/data/crecs-preview-index.json`, and that file is generated **from**
`crecs-property-template/references/catalog/crecs-controls.min.json`. It exists because
Elementor's control stacks do not resolve outside a web request, so the module cannot ask
Elementor and has to carry a projection.

**When this repository's projection changes**, the plugin's index has to be regenerated
and committed there. `build-preview-index.js --check` fails when it drifts — in one
repository that guard was automatic; across two it is a release step somebody has to
remember.

The two sides also agree a contract number: `CONTRACT` in `scripts/crecs_preview.py`
against `'contract'` in the module's REST layer. In one repository that was a constant to
keep in step. Here it is version compatibility between released products.

## Known limitation

`assets/property-template-all-widgets.json` is derived by `build-base-template.js` from a
reference `PropertyPage.json` export that is in no repository at all — it was supplied for
the original audit and lives outside both. **The base template cannot be rebuilt from a
clean checkout**, here or in the plugin repository. Whether that export can be committed
is a decision for whoever owns it.

## Provenance

Extracted from the `crecs-wp-plugin` repository on 2026-09-23, at skill version 1.0.0, as
a clean copy rather than a history split: the commits there mix plugin and skill changes,
so a split would have produced commits whose messages describe WordPress fixes while
containing only Python. The full history of how this was built, audited and tested is in
that repository under `docs/crecs-template-studio/STATE.md`.

The preview module — the live Elementor preview this skill can drive through
`scripts/crecs_preview.py` — is plugin code and stayed there, together with its own
design notes, test plan and connection instructions.
